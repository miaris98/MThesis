## [S-010] `scripts/training/build_feature_cache.py` runs at ~245 frames/s with GPU/CPU both nearly idle
**Date**: 2026-09-14  
**Environment**: Vast.ai RTX 3080 Ti box, 16 vCPU, 62GB RAM, `--num_workers 12 --batch_size 256`, dataset ~85% pixel-cache-hit already.  
**Symptom**: Full-dataset feature-cache build (520k frames) measured at ~245 frames/s steady-state - far below the ~22,000 frames/s single-metric disk read rate and the encoder's own forward-pass throughput measured in isolation (§ validation session, 2026-09-13). `nvidia-smi` showed 0% GPU util / 185W of 280W draw at a random sample; `ps` showed the 12 DataLoader worker processes at ~0.7% CPU each (essentially idle) while the single main process sat at 100% of one core (`free -g`/`/proc/loadavg` confirmed aggregate load ~2 of 16 cores).  
**Root Cause**: Not isolated to one number, but the shape rules out the two obvious suspects:
  - Per-file writes are not the bottleneck: a standalone benchmark of the exact `np.save(tmp) + os.replace()` pattern this script uses hit 4420 writes/s single-threaded (0.23ms/write) - two orders of magnitude above what 245 frames/s needs.
  - Worker-side decode is not the bottleneck either: with ~85% of frames already pixel-cached (from the earlier full training run), most `_load_rgb` calls take the ~0.12ms `np.load()` cache-hit path, not JPEG decode + route-overlay draw + resize.
  - The main process being pinned to 100% of exactly one core while the GPU shows near-zero utilization is the signature of CUDA's default *blocking* host-side synchronization: `feats.float().cpu()` (and the `.to(device)` before it) spin-waits on the CPU rather than yielding the core, so a legitimately fast-but-frequent GPU round-trip per 256-frame batch reads as "CPU pegged, GPU idle" in coarse tools like `nvidia-smi`/`ps` even though the GPU is actually doing the work between polls. The 12 workers stay idle because they can already fill the prefetch queue far faster than the main loop drains it.
**Fix**: Not applied - diagnosed with ~20 min of the run remaining, and restarting to test a fix would have cost more (the ~4min dataset re-index, resumability aside) than it saved. Left as a documented lever for a *future* full cache rebuild (this one only needs re-running if `--img_size`/`--crop_bottom_frac`/`--route_overlay`/`--backbone` changes):
  1. Move the per-batch `feats.cpu().numpy()` + write loop onto a background thread (the pattern `wor_trainer.py`'s checkpoint `save_async` already uses), so the main loop can request the next GPU batch immediately instead of blocking on the transfer+write.
  2. Or set `torch.backends.cudnn.benchmark = True` and increase `--batch_size` well past 256 - larger batches amortize the fixed per-call host-sync cost the CPU is burning on more actual GPU work per round-trip.
  3. Confirm with `torch.profiler` rather than `nvidia-smi` snapshots before committing to either - coarse sampling tools are exactly what made this ambiguous to diagnose live.
**Commit**: (uncommitted - diagnostic only, no code changed)

## [S-011] Leaderboard eval ETA was ~3x wrong: a correctly-measured rate applied to the wrong workload
**Date**: 2026-09-15  
**Environment**: Vast.ai RTX A4000 (16GB), AMD EPYC 7713 128-core, 1TB RAM, CARLA 0.9.15 Leaderboard 2.0  
**Symptom**: A remaining-time estimate of ~40-46h was given for the two-arm closed-loop eval and defended across two turns by decomposing it into genuinely measured quantities (observed sim-to-wall ratio, observed driving speed). The user rejected it from memory: the same evaluation had previously completed in ~14h for both arms on one machine.  
**Root Cause**: The arithmetic was never wrong; the *workload* had silently changed between the two runs and nobody diffed the configs. Recovering the previous run's own results file (`E:\MThesis_EXP\full8town_run\leaderboard_official_out\pilot_cnn.json` - leaderboard checkpoints record `meta.duration_game` and `meta.duration_system` per route, so exact historical per-route wall-clock is always recoverable) showed four compounding differences:

| | previous (~14h) | current |
| --- | --- | --- |
| route file | `routes_training.xml` | `routes_validation.xml` |
| town | Town12 | Town13 (CARLA's largest map) |
| routes/arm | 10 | 20 |
| scenarios/route | ~56 | ~89 |
| sim-to-wall ratio | 1.27x | 0.216x |

Multiplier chain: 2.0x (route count) x 1.79x (game-time per route) x 5.89x (ratio collapse) = ~21x, which reproduces 2.51h -> ~53h exactly. The ratio collapse decomposes further into ~4.1x from Town12->Town13 and ~1.44x from two arms contending on one GPU.

Two non-obvious contributors:
  - **A better model makes closed-loop eval more expensive.** The old run looked cheap partly because the agent was *bad*: "Agent got blocked" on 9 of 10 routes at 5-14% route completion, each terminating after a few hundred seconds of game time. The fixed v3 model drives the routes properly, so episodes run to full length. Never reuse a worse checkpoint's eval wall-clock as the budget for a better one.
  - **Half of `routes_validation.xml` is a weather repeat, not new route coverage.** Routes 10-19 have byte-identical `<waypoints>` and `<scenarios>` XML to routes 0-9 (verified by md5 of the serialized elements); only `<weathers>` differs (route 0 clear/light-fog vs route 10 heavy-rain/100%-wind). Running all 20 is 10 unique routes x 2 weather conditions, so the official run can be halved by dropping 10-19 at the cost of adverse-weather numbers only.

**Fix**: No code change - a process fix. Before quoting or defending any eval ETA, diff the actual config (route file, town, route count, scenario density, GPU, concurrency) against whatever run it is being compared to. When a user says "this took N hours before", treat it as a load-bearing datum and go find the old run's artifacts rather than re-deriving the new estimate more carefully. Checking the sim-to-wall ratio against a known-good historical ratio isolates "the environment got heavier" from "the agent drives further" in a single number.  
**Commit**: (documentation only)

## [S-012] An orphaned CarlaUE4 server held 5.7GB of VRAM and deadlocked the watchdog that was waiting for it
**Date**: 2026-09-15  
**Environment**: Vast.ai RTX A4000 (16GB usable 15.6GiB), 3 parallel eval arms on ports 2000/2010/2020  
**File**: `scripts/eval/run_leaderboard_official.sh`, `eval_watchdog.sh`  
**Symptom**: The third eval arm (`qwen_a`) sat "queued" indefinitely, with `eval_watchdog.sh` logging `only 1556MiB free (< 7000MiB needed) - queued, waiting for another arm to free VRAM` on every cycle for over an hour. The user's hypothesis - "you don't clear the retrys correctly and that is what drains the gpu" - had earlier been investigated and **wrongly dismissed** on the grounds that the watchdog log showed zero relaunches and memory was fluctuating rather than monotonically draining.  
**Root Cause**: `nvidia-smi --query-compute-apps` showed **five** GPU processes for **two** live evaluators. Cross-referencing CarlaUE4 processes against live `leaderboard_evaluator.py` processes found servers on ports 2000, 2010 and 2020 but evaluators only on 2000 and 2020: the port-2010 server was an orphan, running 1h15m with no client. `scripts/eval/run_leaderboard_official.sh` starts a CarlaUE4 server and then installs `trap 'kill $WATCHDOG' EXIT` - which kills only its *results*-watchdog subshell, never the simulator it launched. When `qwen_a`'s evaluator died of CUDA OOM, the script exited and left the server running. That orphan was holding 5.7GB - and the arm blocked on `MIN_FREE_MIB` was blocked by *its own* leaked server from a previous attempt. Killing it took free VRAM from 1,556MiB to 7,235MiB and the queued arm started immediately.  
**Fix**:
1. Killed the orphan; confirmed both live arms unaffected.
2. `scripts/eval/run_fast_eval.sh` (new) owns its server on every exit path: `trap cleanup_carla EXIT INT TERM`, and only kills a server it actually started (a reused server belongs to whoever started it).
3. **Still outstanding**: `scripts/eval/run_leaderboard_official.sh` has the same leak and has not been fixed. Any launcher that starts a simulator must kill it on every exit path, or a crash-restart loop converts each crash into permanently leaked VRAM.

Process lesson: a resource-headroom gate (`MIN_FREE_MIB`) that waits for *someone else* to free memory will deadlock if the thing consuming the memory is the waiter's own leaked child. Gates need a matching reaper. And a user's hypothesis about a system they have watched for hours deserves per-process evidence before being dismissed - "the log shows no relaunches" disproved the wrong mechanism.  
**Commit**: (uncommitted)

## [S-013] `pkill -f <pattern>` killed the SSH session that issued it
**Date**: 2026-09-15  
**Symptom**: A remote cleanup command `kill -9 <pid>; pkill -9 -f "carla-rpc-port=2010"` returned SSH exit code 255 with truncated output, mid-command.  
**Root Cause**: `pkill -f` matches against the *full command line* of every process. The `bash -c "..."` that ssh spawned to run the cleanup had the string `carla-rpc-port=2010` in its own command line, so pkill matched and killed its own invoking shell. The intended target had already been killed by the preceding explicit `kill -9 <pid>`, so nothing was lost - but the same command as the *only* kill step would have terminated the session before doing its job.  
**Fix**: Never let a `-f` pattern match the invoking shell. Two reliable options, both now used:
  - Match the process *name* rather than the command line (see S-014 for the correct way to do that).
  - Use a bracket class so the pattern matches the target but not the literal text in the caller's own command line: `pgrep -f "leaderboard_v3_qwen[_]a\.json"` matches `..._qwen_a.json` while the script's own command line contains `qwen[_]a` and cannot self-match.

**Commit**: (uncommitted)

## [S-014] `pgrep -x CarlaUE4-Linux-Shipping` is a silent no-op: the kernel truncates comm to 15 characters
**Date**: 2026-09-15  
**File**: `scripts/eval/run_fast_eval.sh` (cleanup path)  
**Symptom**: A cleanup function written to avoid S-013 by matching the process name exactly - `for pid in $(pgrep -x CarlaUE4-Linux-Shipping)` - ran without error, reported nothing, and freed no VRAM. A diagnostic listing "surviving CARLA ports" using the same matcher printed an empty list while `nvidia-smi` showed GPU memory had *increased*; the server was still running.  
**Root Cause**: `pgrep -x` matches `/proc/PID/comm`, which the kernel truncates to 15 characters (`TASK_COMM_LEN`). The real binary is `CarlaUE4-Linux-Shipping` (23 chars), so comm is `CarlaUE4-Linux-` and an exact match against the full name can never succeed. The failure is silent in the worst way: the function looks more careful than a `pkill -f`, and leaks the resource it was written to reclaim on every invocation.  
**Fix**: Walk `/proc` and match the comm *prefix*, then confirm with the cmdline:
```
for pid in $(ls /proc | grep -E '^[0-9]+$'); do
  [ -r "/proc/$pid/comm" ] || continue
  case "$(cat /proc/$pid/comm 2>/dev/null)" in CarlaUE4*) ;; *) continue ;; esac
  cmd="$(tr '\0' ' ' < /proc/$pid/cmdline 2>/dev/null) "
  case "$cmd" in *"carla-rpc-port=$PORT "*) kill -9 "$pid" ;; esac
done
```
This is immune to S-013 (a shell's comm is `bash`/`sh`, never `CarlaUE4*`) and catches both the `CarlaUE4.sh` launcher and the Shipping binary, which both carry the port in their cmdline. The trailing space in the port match prevents `2000` matching `20000`. General rule: verify that a process matcher actually matches something before trusting it as cleanup - an empty match set and a successful cleanup are indistinguishable from the exit code.  
**Commit**: (uncommitted)

## [S-015] The official leaderboard eval cannot serve as a hyperparameter-search fitness function
**Date**: 2026-09-15  
**Environment**: Vast.ai RTX A4000 (16GB), EPYC 7713 128-core  
**Symptom**: A full `routes_validation.xml` run costs ~50h per arm (S-011), making it unusable as a signal for hyperparameter search, where dozens of configurations must be ranked.  
**Root Cause**: Profiling showed the cost is not the model and cannot be bought away with hardware:
  - GPU drew 42W of a 140W budget at 7-30% utilization with two arms running; GPU *memory* utilization was 1-5%.
  - 128 CPU cores sat at load average ~30; 1TB RAM, 915GB available.
  - The evaluator runs in synchronous lock-step: the simulator cannot advance a tick until the agent returns a control, so throughput is bound by per-tick round-trip *latency*, not by compute. Neither a faster GPU nor more cores changes it.
  - The heavy parts are Town13's map size and the ~89 scenario behaviour-trees per route ticking in lock-step with the agent.
  - VRAM is the only real ceiling, and it caps *concurrency*: ~5.7-7.2GB per arm means exactly 2 arms fit on a 16GB card. Speedup therefore comes only from more parallel arms, on more cards.
**Fix**: Added `scripts/eval/run_fast_eval.sh`, a cheaper tier over the existing `scripts/eval/eval_wor_closed_loop.py` + `src/eval/driving_metrics.py`. **Date**: 2026-09-15  
**Environment**: Vast.ai RTX A4000, `venv_carla` (Python 3.10, numpy 2.2.6, torch 2.14.0+cu130)

**Symptom**: Bringing TF++ in as a reference model meant importing `carla_garage/team_code/sensor_agent.py` in `venv_carla`. AttributeError: `np.sctypes` was removed in the NumPy 2.0 release.
**Root Cause**: `carla_garage/team_code/requirements.txt` pins `numpy==1.26.4`, `torch==2.5.0`, `imgaug==0.4.0`. `venv_carla` was built for this project's own WoR agent and runs numpy 2.2.6. `imgaug` (last released 2020, unmaintained) uses `np.sctypes`, which NumPy 2.0 deleted. `team_code/data.py` imports `imgaug` at **module scope**, so every import of `sensor_agent` executes it, even though imgaug is only used for training-time augmentation (`data.py:1218-1230`) and inference touches `CARLA_Data` solely for `lidar_to_histogram_features` (`sensor_agent.py:485`).

**The shortcut that was deliberately refused**: stubbing `np.sctypes` back in before importing imgaug would have worked in about three lines, since imgaug is provably unused on the inference path. It was rejected because it defeats the purpose of running TF++ at all. TF++ is in this project for exactly one reason - to reproduce a *published* number so that a mismatch indicts our harness rather than the model. Run it on library versions its authors never tested, and a low score becomes un-attributable between "our harness is wrong" and "torch 2.14 changed a default". **For a calibration anchor, environment fidelity is part of the measurement, not incidental packaging** - the one case where "just make the import work" is the wrong instinct.

**Secondary lesson**: the pre-flight introduced in S-011 was changed to import the agent *by path* rather than a hardcoded module name, so it checks the agent that will actually run. That is what surfaced all four dependency failures in seconds each, instead of after a 60-100s CARLA cold start apiece.  
**Commit**: (see run_leaderboard_official.sh / setup_tfpp_env.sh)

## [S-017] Tier 1 refactored onto the real Leaderboard agent contract; GameTime.restart() ordering silently broke route 2+
**Date**: 2026-09-15  
**File**: `scripts/eval/eval_wor_closed_loop.py`, `scripts/eval/run_fast_eval.sh`  
**Symptom**: After replacing Tier 1's hand-rolled camera+dict policy interface with the real `AgentWrapper`/`SensorInterface`/`GameTime` plumbing (needed so TF++, not just WoR, could run on Tier 1's cheap routes - see eval_tiers_design.md Stage 2), a 3-route regression test reliably drove route 1 correctly and then failed route 2 with `leaderboard.envs.sensor_interface.SensorReceivedNoData: A sensor took too long to send their data`, after a 10-second queue timeout.  
**Root Cause**: GNSS/IMU/speedometer are pseudo-sensors (`leaderboard.envs.sensor_interface.BaseReader`), each backed by a **background thread** that captures `latest_time = GameTime.get_time()` exactly once, at thread-start (which happens inside `AgentWrapper.setup_sensors()`), and only delivers its next reading once the *global, process-wide* `GameTime` clock advances past that captured value. `GameTime.restart()` was being called *after* `setup_sensors()`, once per route, to give each route a fresh sim-time clock (matching what the real evaluator does between routes). For route 1 this was invisible: `GameTime` was already at 0 from process start, so restarting it changed nothing observable. For route 2, the pseudo-sensor thread captured route 1's high *ending* game-time (e.g. 30.0s) as `latest_time` the moment it started - then the very next line reset the clock to 0. `current_time - latest_time` stayed negative for nearly the whole route, so the pseudo-sensor never fired again, and `SensorInterface.get_data()` (which blocks until every declared sensor has delivered a reading for the current frame) timed out waiting for a sensor that would never speak again.  
**Fix**: Moved `GameTime.restart()` to *before* agent construction and `setup_sensors()`, not after. Every route's pseudo-sensor threads now start against an already-reset clock - identical to route 1's situation - rather than racing a reset that happens moments after they've captured a stale reference point.  
**Why this is worth writing down beyond this one call site**: the bug is invisible on the first iteration of any loop that (a) has some per-iteration background thread capturing a *snapshot* of shared mutable state at start-up, and (b) resets that shared state right after the thread starts rather than right before. The first iteration can never expose it, because the state hasn't drifted yet - it will only ever surface starting from the second iteration onward, which is exactly the shape that makes a smoke test with too few iterations (a 1-route check, here) miss it entirely. **How to apply**: when a loop restarts shared global state once per iteration and something inside that iteration spawns a thread that reads the same shared state at start-up, the reset must happen *before* anything that could read the old value, not after - and a regression test for a per-iteration bug needs at least 2 iterations, not 1, or it only ever exercises the always-correct first case.  

**Three smaller bugs found the same way** (by running it, not by review) during the same refactor:
1. `scripts/eval/run_fast_eval.sh`'s `PYTHONPATH` never carried `leaderboard`/`scenario_runner` - Tier 1 never imported them under the old hand-rolled path. `ModuleNotFoundError: No module named 'leaderboard'` on the first line of the new import block.
2. `leaderboard.utils.route_manipulation.location_route_to_gps` (vendored, unmodified) does `transform.location` on its input - it wants `carla.Transform`, not the bare `carla.Location` objects this project's own route-building code has always used. `AttributeError: 'Location' object has no attribute 'location'`. Fixed by wrapping each location in `carla.Transform(loc)` when building the plan handed to the agent.
3. `CarlaDataProvider.get_hero_actor()` (which `WorB2DAgent._get_hero()` calls) searches `_carla_actor_pool` - a *third* dict, distinct from the one `CarlaDataProvider.register_actor()` populates. Only `CarlaDataProvider.request_new_actor()` populates that pool normally; this script spawns the ego directly via `world.try_spawn_actor()` (needed for exact route-origin placement), so nothing had ever added it. `RuntimeError: No hero actor`. Fixed by registering into `_carla_actor_pool` manually - and by explicitly removing the entry on cleanup, since `get_hero_actor()` returns the *first* dict-order match: an un-removed stale entry from route N-1 would silently keep shadowing route N's real hero forever.  
**Commit**: (see eval_wor_closed_loop.py / run_fast_eval.sh)

The run cannot advance past it unaided.

**Root Cause**: Two distinct effects that are indistinguishable in any single log.
  - `client.load_world()` on this box segfaults CarlaUE4 **probabilistically** for the classic towns. Mined from all 58 real load attempts in this run's logs: Town04 4/7 (57%), Town06 3/6 (50%), Town07 3/6 (50%), Town05 2/8 (25%). Overall 28/58 = 48%. This is ordinary background instability, and `--resume=True` does recover from it, because the *client* usually survives long enough to record the failure and move on.
  - Route 27515 / **Town03 is deterministic, not probabilistic: 16 attempts, 16 segfaults, 0 successes**, across many separately booted CarlaUE4 processes spanning 1.5 hours. Under the 50% per-attempt model, 16/16 has probability 0.5^16, about 1 in 65,000 - so this is a different failure, not the tail of the same one. Town03 is effectively unrunnable on this box.

Which towns are *not* affected: Town12 0/6, Town13 0/3, Town10HD 0/2, Town02 0/4.

**This is not a new finding - it independently replicates `challenges_03` section 3.13**, which had already established the same 100% Town03 failure rate (11 of 11 Town03 routes in a 51-route pre-flight probe) and had already identified the mechanism: `Town03_BuiltData.uexp` is 220,361,507 bytes, 130x to 6000x every sibling town's baked-lighting asset (35KB to 1.65MB), and the crash occurs while deserializing it. The identical byte count was measured again here, from a different rental, without knowing 3.13 existed. 3.13 also established that this is an upstream property of the CARLA 0.9.15 release and *not* a corrupted local download - Town03's files carry the same base-release install timestamp as every other working town (verified again here: Town03 and the working Town04 are both `Nov 10 2023`). **That rules out repairing or re-extracting Town03 locally: any re-extract of the same release reproduces the same 210MB asset and the same crash.** Disk (550GB free), RAM (82GB available) and VRAM were all healthy at crash time, matching 3.13's isolated retest on an otherwise-idle system.

What this entry adds beyond 3.13 is (a) the *background* segfault rate for the other towns on this rental - 48% overall, Town04 57%, Town06 50%, Town07 50%, Town05 25% - which is what makes Town03's 16/16 legible as categorically different rather than merely worse; and (b) the operational consequence 3.13 did not hit, below.

This is **not** the failure in `docs/guides/carla_vulkan_driver_troubleshooting_guide.md`: that one is `EXIT CODE: 1` with no signal and no log, at startup, with `-vulkan` and `-opengl` failing identically. This one is a signal crash mid-run, on a server that has already rendered thousands of frames.

**Fix**: Not yet applied - route 27515 must either be dropped from the subset (leaving a 19-route comparison) or accepted as a permanent crash record for every arm. It is at least *symmetric*: all three arms fail it identically, so it drags all means down without biasing the comparison. It must not be left in the loop untouched, because the supervisor will retry it forever and burn rented box time at ~7 relaunches per 90 minutes per arm.

**The methodological error is the part worth keeping.** The first hypothesis was "Town03 specifically is broken". It was tested with one standalone `load_world` per town, and the *control* - Town06 - segfaulted before the test ever reached Town03. That single observation was reported as refuting the hypothesis. It did not. Town06 fails 50% of the time: the test flipped a coin once and the result was read as a proof. The original hypothesis was substantially correct and the confident retraction was wrong.
**How to apply**: before letting one trial refute a hypothesis, establish the base rate of whatever is being used as a control. A control that is itself ~50% flaky carries almost no information at n=1; it needs an n where 0.5^n is actually small. And here the decisive evidence cost nothing and was already on disk - 58 load attempts across the run's own logs, which separate a 100%-deterministic failure from a 50%-flaky one at a glance. Mine the logs you already have before generating new samples, especially when new samples compete for the same GPU as the run you are debugging.

**The second, larger error: the project had already answered this.** The whole investigation above - the isolation test, the retraction, the log mining - re-derived a conclusion that `challenges_03` 3.13 already stated, including the same byte count, from a file in this repository. Nothing was searched for prior art until after the analysis was finished and the user asked for it directly. The cost was not a wrong answer (the final answer matches 3.13) but an entire debugging session, a GPU-competing test on the box being debugged, and one confidently-published retraction of a correct hypothesis. This is the index's own "a rule written down is not a rule enforced" theme at its most literal: the finding was written down, in a file named for exactly this class of problem, and nothing caused it to be read.
**How to apply**: when a symptom involves a named, enumerable entity of this project's domain - a town, a route id, a map, a dependency pin - grep `challenges/` and `docs/design/struggle-solutions.md` for that literal token *before* forming a hypothesis, not after. `grep -rn Town03 challenges/` would have returned the answer, with its mechanism, in under a second.
**Commit**: (documentation only)

## [S-019] A liveness check using `pgrep -f "checkpoint=<path>"` matched an unrelated watcher and silently disabled auto-restart for 40 minutes
**Date**: 2026-09-16
**File**: `scripts/sync/guardian.sh` (restart supervisor for each eval arm)
**Symptom**: `scripts/sync/guardian.sh` polls every 15s and relaunches an arm whose evaluator has died. cnn and qwen died and stayed dead for over 40 minutes with GPU 0 completely idle (2 MiB used), while both guardian processes were alive and sleeping normally. Their log files (`guardian_logs/b2d20_cnn.log`, `..._qwen.log`) did not exist at all - the "dead, relaunching" branch had never been taken once in roughly 220 iterations. TF++'s guardian, running byte-identical code, was restarting its own arm correctly the whole time.
**Root Cause**: The liveness test is

```bash
if ! pgrep -f "checkpoint=$CKPT_JSON" >/dev/null 2>&1; then ... relaunch ... fi
```

A *separate* helper, left over from the "move TF++ onto GPU 0 once cnn+qwen finish" plan, was running in the background:

```bash
bash -c "while pgrep -f 'checkpoint=/workspace/bench2drive_out/b2d20_cnn.json' >/dev/null \
      || pgrep -f 'checkpoint=/workspace/bench2drive_out/b2d20_qwen.json' >/dev/null; \
      do sleep 20; done; echo GPU0_FREED"
```

That helper's own command line contains the literal text `checkpoint=/workspace/bench2drive_out/b2d20_cnn.json`, so `pgrep -f` matched *it* and reported the evaluator as alive indefinitely. The guardian was neither broken nor hung - it was being told, accurately, that a process matching its pattern existed. Killing the helper made both guardians fire within 15 seconds and both arms relaunched immediately. TF++ was spared only because that helper happened to name cnn and qwen but not tfpp.
**Fix**: Match something only the real process can carry. The cheapest correct version here is to require the program name as well, e.g. `pgrep -f "leaderboard_evaluator.*checkpoint=$CKPT_JSON"`, or use the S-013 bracket trick (`b2d20_[c]nn.json`) so that any watcher that spells the name literally cannot match.

**Relation to S-013 / S-014 - same family, third variant, and the failure *direction* is what matters:**
  - S-013: `pkill -f` matched the *invoking shell* -> killed the wrong process (false positive, destructive, loud).
  - S-014: `pgrep -x` matched *nothing* because comm is truncated to 15 chars -> cleanup silently no-op (false negative, leaks the resource).
  - S-019 (this one): `pgrep -f` matched an *unrelated third process* -> a liveness check that can never report death (false positive, silently disables recovery).

**How to apply**: any `pgrep`/`pkill -f` pattern that is also *written down* as literal text in some other script's command line will match that script. When the pattern decides "is X still alive", a false positive is worse than a crash: the supervisor stays healthy and idle while the thing it supervises is gone, and the only symptom is an absence - no log lines, no restarts, an empty log file that looks the same as "nothing has gone wrong yet". Assert the matcher's selectivity once at startup (expect exactly 1 match while the arm is up, 0 while it is down) instead of trusting it, since an unexercised branch in a supervisor is indistinguishable from a working one.
**Commit**: (uncommitted)

## [S-020] Recovery-data gap diagnosed for cnn/qwen's closed-loop failures; the obvious cheap fix turned out already half-built, and its data half-missing
**Date**: 2026-09-16
**File**: `src/training/wor_dataset.py`, `src/training/wor_trainer.py`, `scripts/setup/download_pdm_lite.py`, `Carla-utils/carla_garage/team_code/data_agent.py`
**Symptom**: The 20-route Bench2Drive comparison (see `challenges_03` 3.15) showed cnn/qwen median route completion of 22-27% against TF++'s 100%, with `outside_route_lanes` (0.67/0.47 per route) and `vehicle_blocked` (0.40/0.47 per route) as the dominant infractions, against near-zero `collisions_vehicle`/`red_light` rates comparable to TF++. Route-level detail (`classify_failures.py` / `infractions.py` on the pulled checkpoint JSONs) shows both students leaving the route corridor early and never recovering, not failing at traffic reasoning.

**Root Cause, first pass**: This looks like a distribution-shift signature rather than a wrong-loss-axis one. Pure behaviour cloning trains only on the expert's own trajectory, which is centered and correctly heading by construction - it contains no example of "I am 0.5m off-center, what do I do." Once the policy drifts even slightly at inference, it is extrapolating into a region the loss function never touched, and `vehicle_blocked` with zero recovery is exactly what that produces. Checked `wor_dataset.py` directly: there is no perturbation, jitter, or recovery augmentation anywhere in it. This is a real, untried gap - distinct from the `heading_loss_weight`/`curvature_loss_weight` axis-reweighting already tried on `qwen30m_geom_s0` and already found (Group 13.29/13.33, replicated by this run's cnn-vs-qwen tie) not to move the needle at the seed counts tested.

**Correction made same day, before anything was implemented**: the first proposal for a fix - "jitter the ego pose and analytically recompute the corrective waypoint label from route geometry, purely offline" - is unsound as stated. The waypoint *label* is a function of pose, but the training *image* is a fixed rendered frame; recomputing only the label while leaving the image unchanged creates a supervision pair where the picture still shows the on-route view but the label says "steer hard to recover" - the network would learn a corrective label attached to a centered-looking image, which is a worse dataset than doing nothing. Recovery augmentation is only valid when the *image* is re-rendered from the perturbed pose too (the classic CIL/DAVE-2/LBC "triple camera" trick), not synthesized from the label side alone.

**What already exists, found by reading `data_agent.py` rather than continuing to reason about it from outside**: `DataAgent` (the carla_garage class that produced this project's PDM-Lite training data) already implements the correct version of exactly this. On `self.config.augment`, it mounts a second RGB/semantic/depth camera at a per-route-fixed random translation and yaw offset (`camera_translation_augmentation_min/max`, `camera_rotation_augmentation_min/max`) and genuinely renders and saves it as `rgb_augmented/` alongside the on-route `rgb/`. This is a real second render, not an approximation, so it does not have the label/image mismatch above - it is production-grade recovery data, already built, unused.

**Resolved same day, before any code was written**: checked the actual HuggingFace file tree rather than trusting the `scripts/setup/download_pdm_lite.py` comment's inference. Listed a real archive's contents via HTTP Range requests against the zip's central directory (`zipfile.ZipFile` fed a small range-request-backed file-like object, so this cost a few KB of transfer, not the 434MB archive) - `Town01/data/ControlLoss.zip` contains 10,094 entries, 3,668 of them under `rgb_augmented/` paths (e.g. `ControlLoss/Route0_Rep0/rgb_augmented/0131.jpg`). The `scripts/setup/download_pdm_lite.py` comment was wrong, or referred to a leaner subset that is not what actually ships. **The augmented camera IS in the released dataset.** Better still, each `measurements/*.json.gz` file carries `augmentation_translation` and `augmentation_rotation` (confirmed present, sample values 0.89m / -2.61 degrees) - the exact per-frame offset needed to transform the future-`ego_matrix`-chain waypoint computation `_index_pdm_lite_route` already does for the on-route camera into the correct corrective target for the augmented camera. Nothing about this requires new CARLA time; it only requires re-downloading (or supplementing an existing download of) the towns already in use, since `scripts/setup/download_pdm_lite.py`'s `extractall` does keep these files - they simply were not read by `wor_dataset.py` afterward.

**Status**: Data path fully specified, still OPEN on implementation. What remains is entirely in `wor_dataset.py`:
1. Extend `_index_pdm_lite_route` to emit a second sample per frame when `rgb_augmented/{frame}.jpg` exists, pointing `rgb_path` at the augmented image.
2. For that sample's waypoint targets, do not reuse the on-route `ref_inv @ fut["ego_matrix"]` transform as-is - compose it with the frame's own `augmentation_translation`/`augmentation_rotation` (a lateral offset + yaw rotation of the reference frame before inverting) so the label reflects "how to get from the augmented camera's actual position back onto the route," not "how to get from the original centered position onward." This is the corrected version of the flawed first proposal above, now with real numbers to implement it correctly.
3. `wor_trainer.py`'s existing `lateral_loss_weight`/`heading_loss_weight`/`curvature_loss_weight` machinery needs no changes - this only adds *samples*, not a new loss term.
Option 2 (on-policy DAgger via `autopilot.py`) is unaffected by this finding and remains the higher-cost, higher-ceiling alternative if recovery augmentation alone is insufficient.

**Nothing above has been implemented or trained on yet** - the data path is now fully specified (previous paragraph) but `wor_dataset.py` has not been touched. No qwen/cnn retrain should be described as testing "recovery-data" until the loader change lands and produces new training samples - a retrain launched before that would just reproduce the existing checkpoints' behaviour under a different seed and consume retrain budget without testing the hypothesis this entry exists to test.

**Commit**: (diagnosis and documentation only, no code changed)

## [S-021] Dropping one route from `--routes-subset` under `--resume=True` silently wiped 15 of 16 completed cnn results
**Date**: 2026-09-16
**File**: `Carla-utils/carla_garage/Bench2Drive/leaderboard/leaderboard/utils/route_indexer.py:65-67`
**Symptom**: After deciding to drop the permanently-crashing route 27515 (Town03, see `challenges_03` 3.15) from the 20-route subset and relaunching all three arms on the remaining 19, cnn's checkpoint immediately read `progress: [1, 19]` with a single record - 15 of its 16 completed routes (including two `Completed` results worth 100.0 and 60.0 DS) had vanished and the evaluator was re-driving route `2050` from scratch. qwen and TF++ were saved only because their guardians were still inside `scripts/eval/run_bench2drive.sh`'s 45s stagger sleep when the loss was caught and everything was killed - they were seconds from the same fate.
**Root Cause**: `RouteIndexer.validate_and_resume()` (`route_indexer.py:65`) does `if progress[1] != self.total: return False` before anything else - `self.total` is `len(routes_subset)`, and `progress[1]` is the checkpoint's *stored* route count from the run that produced it. Any change to `--routes-subset` that changes the resulting count fails this check unconditionally, and the caller (`leaderboard_evaluator.py:470-473`) responds to `resume=False` by calling `self.statistics_manager.clear_records()` - discarding every existing record, not just the ones affected by the subset change, before running a single new route. This is a coarser trigger than it looks: the check does not care *which* routes changed or *where* - only whether the resulting total number differs at all - so removing one crashing route in the middle of an otherwise-untouched subset was enough to invalidate a checkpoint whose first 16 route IDs were still byte-identical to the new subset's first 16.
**Fix**: Before changing `--routes-subset` on an existing `--resume=True` run, hand-patch each checkpoint JSON's `_checkpoint.progress[1]` to match the *new* subset's route count (`len(new_routes_subset) * repetitions`) and leave `records` untouched:
```python
import json
p = "/workspace/bench2drive_out/<label>.json"
d = json.load(open(p))
d["_checkpoint"]["progress"][1] = new_total_route_count
json.dump(d, open(p, "w"))
```
This is safe specifically because `validate_and_resume`'s *second* check (`route_indexer.py:71-88`) re-verifies every already-completed record's `route_id` against the new subset's route list position-by-position up to `progress[0]`, and only accepts the resume if they still match exactly - so the patch cannot silently paper over a case where positions actually shifted (e.g. dropping a route *before* completed ones would fail this second check honestly, rather than resuming against misaligned records). Confirmed working: patched all three checkpoints' `progress[1]` from 20 to 19, relaunched, and cnn correctly resumed to `[16, 19]` (later `[17, 19]`) with all 16 prior records - including both zero'd-out `Completed` routes - intact.
**Why the removed route's position mattered, and would not always be this safe**: 27515 was the second-to-last route in the original 20-route ordering, after all 16 already-completed routes. Every record from index 0 to 15 kept the identical position in the trimmed subset, so the per-record `route_id` re-check at `route_indexer.py:79` passed cleanly. Had the dropped route sat *before* any already-completed route instead, every later record's position would have shifted by one and the same re-check would have (correctly) refused to resume rather than silently misattributing scores to the wrong route - the progress[1] patch is not a general "delete a route safely" recipe, it only works when nothing already-recorded sits after the dropped route in list order.
**No data lost in the end** - cnn's wiped checkpoint was restored from a full local+`E:\MThesis_EXP` backup pulled minutes earlier for an unrelated reason (see the route-representativeness analysis), which is the only reason this cost fifteen minutes rather than fifteen re-driven routes. Recommend backing up a checkpoint JSON immediately before touching `--routes-subset` on any run holding results that took real box-time to produce, since this behaviour is silent - the evaluator prints nothing indicating a wipe happened, `resume=False` just falls through to normal "start fresh" behaviour.
**Commit**: (uncommitted; harness/process fix, no code changed - `route_indexer.py` is vendored and unmodified)

## [S-024] The Atari GTrXL + EfficientZero v2 agent had no reinforcement-learning objective - the policy loss was pure self-imitation on replay-buffer actions
**Date**: 2026-09-17
**File**: `atari_qwen/training/train_gtrxl_ez2.py`, `train_gtrxl_ez2_turbo.py`, `optimize_gtrxl_optuna.py` (fixed in commit `049da8e`)
**Symptom**: none visible in training logs - loss curves looked normal, `reward_loss`/`consistency_loss` decreased as expected, SPS and GPU utilization were healthy. Caught only via an external architectural review requested mid-session, not by any metric the training loop itself surfaced.
**Root cause**: across all three Atari trainers, `total_loss = policy_loss + reward_weight * reward_loss + consistency_weight * consistency_loss`, where `policy_loss = F.cross_entropy(logits_0, b_actions[:, 0])` - `b_actions[:, 0]` being whatever action the replay buffer happened to record when that transition was collected (an epsilon-greedy/argmax-of-self mixture). This is behaviour cloning on the agent's own past actions, not policy improvement: reward never entered the policy objective anywhere. `critic_head` and `predictor.value_head` were both instantiated (the critic head even carried a deliberate PPO-style orthogonal `gain=1.0` init, signalling actor-critic intent) and both were computed every step but never referenced by any loss term in any of the three trainers - dead parameters receiving zero task gradient. The Optuna hyperparameter search (`optimize_gtrxl_optuna.py`) was tuning `consistency_weight`/`reward_weight` around this frozen imitation term, meaning 15 trials would have measured which auxiliary-loss balance best exploited a policy that could never improve with reward, not which hyperparameters produce better Atari play.
**Why this is a dangerous class of bug**: every component that *looked* like a working actor-critic RL system was present and individually correct (GRU-gated transformer trunk matching Parisotto et al.'s formula exactly, a properly asymmetric SimSiam consistency loss with correct stop-gradient placement, a sensible value head with sensible init) - the defect was not in any one module but in which tensors the training loop's loss function actually referenced. Nothing crashed, nothing produced NaN, and the eval loop's reported score would have looked like "the architecture isn't learning very well" rather than "the architecture is never being asked to learn to maximise reward at all" - the same silent-failure shape this project's `challenges_00` cross-cutting theme names as its most expensive failure mode, recurring in a system built independently of the CARLA/WoR codebase this project's own documentation habits grew out of.
**Fix** (commit `049da8e`, same day): wired up a real bootstrapped n-step value target (`root_value_loss` + `unroll_value_loss`, both `smooth_l1_loss` against bootstrapped returns), replaced the bare cross-entropy term with an advantage-weighted policy gradient (`-(act_log_prob * adv_norm).mean()`), and added an entropy bonus (`ent_coef`) for exploration - turning this from a representation-learner-with-an-imitation-head into an actual actor-critic objective. Applied across both trainers and the Optuna search space (now also tuning `value_weight` and `ent_coef`).
**Status of the study re-run under the fix**: a fresh 15-trial Optuna study was launched same-day after the fix. At the time the box was destroyed, 2 of 15 trials had completed, both scoring exactly 0.0 on Breakout at the 50k-step-per-trial budget, with a third trial in progress. Two zero scores in a row on Breakout at this budget is not by itself damning (Breakout commonly reports exactly 0 whenever the agent loses all lives before breaking a single brick, which is common in a small step budget regardless of algorithm correctness), but it means the fix has not yet been validated as producing above-baseline play - only confirmed as producing a *correct* actor-critic gradient, not yet confirmed as a *sufficient* one at this budget. The study database (`atari_gtrxl_optuna.db`, 2 complete trials) and full log were pulled to `E:\MThesis_EXP\atari_gtrxl_optuna_20260917\` before the box was destroyed; no per-trial model checkpoints exist to lose (this Optuna objective function never calls `torch.save`, only the standalone `train_gtrxl_ez2*.py` entry points do).
**Commit**: `049da8e` (fix), study results archived, not committed (experiment output).

## [S-025] The S-024 RL-objective fix still collapsed to a constant action under real training — unclamped off-policy policy-gradient log-probs
**Date**: 2026-09-18
**File**: `atari_qwen/training/train_gtrxl_ez2_turbo.py:302-333` (policy loss + `evaluate_agent`'s eval loop), `atari_qwen/training/optimize_gtrxl_optuna.py:156-170` (same policy loss, Optuna search space)
**Symptom**: A fresh 15-trial Optuna study launched same-day under the S-024 fix (`049da8e`) was running live when this session started (started 06:26, 100k-steps-per-trial budget, PID 3834 + 16 vectorized env workers) and had already logged `Eval Score: 0.00` at every checkpoint from step 10,000 through 60,000 on trial 1 — well past the point S-024 flagged as "not yet validated as sufficient." A hand-run 10-episode baseline in `atari_qwen/scripts/test_10_runs.py` separately scored a 1.0-2.0 mean, i.e. a checkpoint trained under the "fixed" objective was being outscored by that baseline.
**Root cause investigation**:
1. Ruled out an observation-normalization mismatch — `ImpalaCNNEncoder.forward` (`atari_qwen/models/visual_encoders.py:119-123`) casts and divides by 255 identically whether called from `evaluate_agent` or the training loop, so eval/train preprocessing is not the divergence.
2. Noticed `atari_qwen/scripts/test_10_runs.py`'s "random" baseline wasn't actually uniform-random: it excluded FIRE from the random pool and force-fired on every life loss/30-step stall (`np.random.choice([0, 2, 3])` plus a scripted relaunch), which guarantees paddle motion and ball relaunch — a heuristic, not a fair random-policy sanity check. Rewrote it to true `np.random.randint(0, n_actions)` per step with no scripting.
3. Added `[EVAL ACTIONS]` histogram logging to `evaluate_agent` (counts every action taken, forced-FIRE included, printed with action names) — the missing instrumentation that let a fully collapsed policy go unnoticed for 60k+ steps in the live study, since it only ever reported a scalar score.
4. First fix attempt: raised the entropy coefficient (`0.01` -> `0.04`) and the epsilon-greedy floor (`0.01` by step 40k -> `0.1` held through the full 100k-step run), reasoning the policy had suffered a classic early exploration collapse. Killed the live study (`pkill -f optimize_gtrxl_optuna.py`) and ran a clean 20k-step confirmatory run under this fix. Result: a bit-for-bit **identical** `NOOP:590 (96%), FIRE:25 (4%)` histogram at every eval checkpoint (5k/10k/15k/20k), score 0.00 throughout — the fix had zero effect on the greedy policy's behaviour.
5. That run's loss log showed why: `PLoss` swings unboundedly and never converges — `-8.6` (step 5k) -> `-113` (10k) -> `-277` (16k) -> `-674` (17k) -> flips sign to `+685` (19k) -> `-453` -> `+195` (20k). Root cause: `act_log_prob = log_probs.gather(...)` feeding `policy_loss = -(act_log_prob * adv_norm).mean()` is unclamped. Batches are drawn from a shared replay buffer (`replay_ratio=2-3`, capacity 60k-100k) holding transitions collected under earlier, stale versions of the policy — ordinary off-policy replay, but this policy-gradient update has no importance-sampling correction or clipping (unlike PPO). Once the greedy policy drifts even slightly toward one action, any replay sample whose recorded action disagrees gets near-zero probability under the *current* policy, so its `log_prob` swings to large negative magnitude; multiplied by `adv_norm` (itself only clamped to ±5), a handful of such samples can still dominate the 256-sample batch mean — consistent with the observed PLoss magnitudes reaching the hundreds. The entropy bonus added in step 4 could not correct this because entropy's gradient vanishes as a policy saturates toward one-hot — by the point the corrective signal is needed most, it has already disappeared.
**Fix**: clamp `act_log_prob` to `min=-10.0` before multiplying by `adv_norm`, in both `train_gtrxl_ez2_turbo.py:328` and `optimize_gtrxl_optuna.py:169`. Bounds how much any single stale/rare off-policy sample can distort one gradient step, without the larger rewrite of adding a full PPO-style importance-sampling ratio.
**Also hit while debugging this**: a relaunch attempt structured as `ssh ... "... & disown; ..." &` (backgrounding the whole SSH invocation locally, on top of backgrounding+disowning remotely) silently produced *no* remote process and an empty log — no error surfaced anywhere, from either layer. Fix: background only at the remote `nohup ... & disown` layer and let the local `ssh` call run in the foreground (or let the tool's own timeout move it to background) rather than stacking a second `&` locally.
**Status of validation**: a second 20k-step confirmatory run under the clamp fix was launched (`results/atari_gtrxl_ez2_confirm2`) immediately after applying it; not complete at the time of writing this entry. Not yet confirmed whether clamping alone is sufficient, or whether the deeper fix (proper importance-sampling / PPO-style clipping for off-policy replay data) will still be needed.

## [S-027] PPO-style clipped-surrogate fix (importance-sampled off-policy correction) stabilized training but did not break the collapse from S-026 — and its trust region may make escape harder, not easier
**Date**: 2026-09-18
**File**: `atari_qwen/training/train_gtrxl_ez2_turbo.py` (policy-loss section, rollout action selection, `VectorizedTrajectoryReplayBuffer`), `atari_qwen/training/optimize_gtrxl_optuna.py` (mirrored)
**Fix implemented** (the deeper fix S-026 flagged as "not yet done"): replaced the plain advantage-weighted REINFORCE update with a proper PPO-clipped surrogate objective. Concretely: rollout action selection now *samples* from `Categorical(probs=softmax(logits))` instead of taking `argmax`, so the collected action genuinely reflects a stochastic policy; the true behavior-policy probability of the taken action under the eps-greedy mixture (`b(a|s) = eps/|A| + (1-eps)*policy(a|s)`) is computed and stored per-transition in a new `logp_buf` array on the replay buffer (warmup transitions get the exact `log(1/action_dim)`, since they're genuinely uniform-random, no forward pass needed); the loss then computes `ratio = exp(clamp(new_logp - old_logp, -20, 20))` and uses `-min(ratio*adv_norm, clip(ratio, 0.8, 1.2)*adv_norm).mean()` in place of both the old REINFORCE term and the S-025 ad-hoc `act_log_prob` clamp, which this supersedes.
**Symptom / validation result**: a 40k-step run (`results/atari_gtrxl_ez2_ppoclip`) under this fix. `PLoss` is now extremely stable throughout — roughly `-0.06` to `+0.0` at every single logged step, none of the S-025/S-026 oscillation or unbounded growth. **But the eval action histogram never escaped a frozen constant-action collapse**: `[EVAL ACTIONS] FIRE:25 (4%), RIGHT:590 (96%)` at step 5,000, then `NOOP:590 (96%), FIRE:25 (4%)` identically at steps 10,000 / 15,000 / 20,000 / 25,000 / 30,000 / 35,000 — six consecutive identical checkpoints, score 0.00 throughout. This run never reached the score-11 peak that the *unstable*, unclipped S-026 run achieved at its step-5,000 checkpoint before relapsing — by this measure PPO-clip alone did strictly worse than the previous attempt.
**Interpretation**: the clip fix is confirmed effective at what it targeted (bounding any single sample's gradient contribution -- no more runaway/oscillating loss), consistent with S-025/S-026's diagnosis of *why* training was unstable. But stability and un-collapsing are different problems. A plausible mechanism for why it may actively hurt escape: PPO's `[0.8, 1.2]` ratio clip is a trust region -- it limits how far the policy can move in any single update *in either direction*, including the large corrective move that would be needed to escape an already-collapsed, highly-peaked action distribution. The earlier unclipped run's occasional huge (and generally dangerous) updates happened, by chance, to produce one large corrective jump early (the step-5,000 score of 11); a trust-region-constrained policy cannot take that kind of jump, so once collapsed early (which still happens fast, by step 5,000-10,000, regardless of the clip), it is stuck taking many small clipped steps with no guarantee they add up to an escape within a modest step budget.
**Not yet resolved**: what actually causes the *initial* collapse-by-step-5000-10000 in the first place (before staleness/instability even has time to compound) remains unexplained by S-025/S-026/S-027 alone. Next lever being tried: widening `num_envs` (16 -> 32, `train_gtrxl_ez2_turbo.py`/`optimize_gtrxl_optuna.py` defaults) to collect proportionally more fresh, current-policy transitions per gradient update (reducing the replay buffer's effective reuse/staleness ratio from roughly 32x to 8x at the same `replay_ratio=2`, `batch_size=256`), on the hypothesis that if the buffer is fresher to begin with, the same entropy bonus and PPO clip may be enough to prevent the early collapse rather than needing to escape it after the fact. This box has 72 CPU cores and was only using 16 (env stepping is not the bottleneck -- GPU-bound gradient updates are), so there is substantial headroom for this without a throughput cost.
**Commit**: (uncommitted -- PPO-clip fix applied and synced to the training box, not yet committed to git).

## [S-028] Widening num_envs (16 -> 32) did not prevent the collapse -- and the replay buffer never actually cycled, so the staleness hypothesis was not properly tested
**Date**: 2026-09-18
**File**: `atari_qwen/training/train_gtrxl_ez2_turbo.py` (`num_envs` default changed 16 -> 32, same for `optimize_gtrxl_optuna.py`'s `objective()`)
**Context**: this box has 72 CPU cores and env stepping was found to not be the throughput bottleneck (GPU-bound gradient updates are), so `num_envs` was widened on the theory that more fresh, current-policy transitions arriving per gradient update would reduce the replay buffer's effective staleness -- the mechanism S-025/S-026/S-027 kept implicating in the collapse.
**Symptom**: 60k-step run (`results/atari_gtrxl_ez2_parallel32`) with `num_envs=32` on top of the already-validated S-027 PPO-clip fix. `PLoss` stayed smooth and stable the entire run (same as S-027, `-0.06` to `+0.0` range, no oscillation) -- confirming training itself is well-behaved. **Root cause of why this test didn't actually test what it intended**: `buffer_capacity` was left at its default (100,000 in `train_gtrxl_ez2_turbo.py`) while this run only collected 60,000 transitions total. Since `VectorizedTrajectoryReplayBuffer` is a circular buffer that only starts evicting old entries once `ptr` wraps around at `capacity`, and 60,000 < 100,000, **the buffer never wrapped** -- every training batch for the entire run was drawn uniformly from the *complete* history back to step 0 (including the earliest, near-fully-random warmup/exploration data), exactly as staleness-prone as the `num_envs=16` runs before it. Widening `num_envs` only speeds up how fast fresh data *arrives* into the buffer; it does nothing to how much old data remains eligible for sampling once the buffer is non-evicting. The actual lever for bounding staleness is `buffer_capacity` relative to `total_steps`, which was not adjusted.
**Not yet resolved / open questions for the next attempt**: (1) whether shrinking `buffer_capacity` (e.g. to ~10k-20k, so it actually cycles within a 40-60k-step test and batches stay recent) changes the outcome -- this is the properly-controlled version of the staleness test S-028 intended to run; (2) whether the advantage normalization (`(adv_0 - adv_0.mean())/(adv_0.std()+eps)`, clamped +/-5, computed per-256-sample-minibatch) is itself injecting large-magnitude noise when the batch's true signal is near-zero (as it likely is under Breakout's reward sparsity, especially once already collapsed and generating short, repetitive, low-diversity trajectories) -- not yet investigated; (3) whether 20k-60k steps is simply too short a budget for entropy-driven exploration to matter at all on a sparse-reward Atari task, independent of any remaining bug -- also not yet isolated from the above.

## [S-035] Root cause finally isolated: the GTrXL's GRU skip-gates are still frozen near their conservative init after 15k-60k steps, making the actor's output input-invariant regardless of training algorithm -- reframes the entire S-024-S-034 investigation
**Date**: 2026-09-18
**File**: `atari_qwen/models/gtrxl_layers.py` (`GRUGating`, `bg_init=2.0`), `atari_qwen/scripts/diagnose_policy_collapse.py` (new diagnostic)
**Trigger**: S-032 (off-policy, GAE, 60k steps) and the on-policy rewrite's own 50k-step run (S-034's follow-up) both converged to the *exact same* score (11.00) with the *exact same* eval action histogram (`FIRE:45 3%, LEFT:1280 97%`), and the same handful of 0.00 variants (`FIRE:600 100%`, `NOOP:590/FIRE:25 96%/4%`). Two structurally different training algorithms landing on bit-identical numbers is too specific to be independent learning -- it demanded a direct check of what the network is actually doing, rather than continuing to infer root cause purely from eval score trajectories.
**Diagnostic**: wrote `atari_qwen/scripts/diagnose_policy_collapse.py`, which feeds a battery of wildly different observations (all-zero frame, all-255 frame, random noise, and 5 genuinely different real gameplay frames from different points in an episode) through a saved checkpoint and reports the actor logits for each.
**Result -- both checkpoints show the same pathology**:
  - On-policy 50k checkpoint (`atari_gtrxl_ez2_onpolicy_50k`, scored 11.00 at its final eval): logits identical to 3 decimal places across all 9 inputs (`[-0.100, 0.019/0.020, -0.015, 0.081]` everywhere), argmax always `LEFT`.
  - Off-policy 60k checkpoint (`atari_gtrxl_ez2_gae_60k`, S-032): same pattern, logits `[-0.013, -0.046, -0.142, 0.135]` identical across all 9 inputs, argmax always `LEFT`.
  - In both checkpoints, every `GRUGating.bg` parameter (8 gates total: 4 GTrXL blocks x 2 gates each) is still at essentially its 2.0 initialization value (all checkpoints measured mean 2.0000-2.0006, min/max within +/-0.007) after the full training budget.
**Root cause**: `GRUGating`'s update rule is `out = (1 - z) * x + z * h_tilde` with `z = sigmoid(w_z(x) + u_z(y) - bg)`. At `bg=2.0`, `z = sigmoid(-2.0) ~= 0.12`, so each gate lets only ~12% of the freshly computed attention/FFN output through, keeping ~88% of the prior (largely input-independent) token value. This is the standard "Stabilizing Transformers for RL" (Parisotto et al. 2020) trick, and it is *supposed* to open up as `bg` is trained down over the course of training -- but `bg` is a learned parameter that receives gradient only indirectly (through the loss's sensitivity to the gated output), and with 8 such gates compounding (4 blocks x 2 gates/block), roughly `0.88^8 ~= 36%` of any single gate's worth of new information survives to the output even if one gate opened partway -- and here `bg` hasn't moved at all. DeepMind's original GTrXL work trained on the order of hundreds of millions to billions of environment frames (DMLab-30); every training run in this investigation (S-024 through S-034) used 15,000-60,000 environment steps, 3-5 orders of magnitude below that regime. The actor and critic heads are consequently making decisions almost entirely from the input-independent `state_token`/`policy_token` learned parameters (themselves initialized at `std=0.02`, i.e. also small), not from anything the visual encoder is extracting from the current frame.
**This reframes the whole investigation**: none of S-025 (PPO-clip), S-027 (importance sampling), S-028 (buffer capacity), S-030/S-031/S-032 (GAE-within-buffer), or S-033/S-034 (per-env exploration, on-policy rewrite) were wrong to fix -- they were all real bugs or genuine architectural improvements, and the on-policy rewrite in particular is still the right design per S-029's comparison. But none of them could have produced a genuinely learning, climbing score curve at these step budgets, because the trunk was never letting visual information reach the policy/value heads in the first place. The "11.00 vs 0.00" oscillation across every run in this whole thread is not policy learning flipping between good and bad behaviors -- it is a frozen, near-constant network's fixed argmax action interacting with the eval harness's scripted `action = 1` (FIRE) override on life-loss/stuck-detection, against a fully deterministic emulator (fixed seed 999, no sticky actions) -- which reproduces an identical score for any checkpoint whose frozen constant action happens to be the same.
**Not yet decided**: the fix. Candidates to weigh: (a) lower `bg_init` substantially (e.g. 0.0 or negative) so gates start more open, trading some of the original training-stability benefit for faster adaptation within a realistic step budget for this project; (b) a much longer training run (hundreds of thousands to low millions of steps) to let the existing conservative gates open naturally, at significant additional compute cost; (c) some other init/architecture change (e.g. warm-starting `bg` lower and annealing it up, or removing GRU gating in favor of plain residual connections given the step budget available). This needs a decision before further training runs are launched, since every run so far has been testing symptoms of this root cause rather than the root cause itself.
**Commit**: (uncommitted -- diagnostic script `atari_qwen/scripts/diagnose_policy_collapse.py` added and synced to the training box).

## [S-045] EfficientZero baseline ran 4.5x slower than it should have: LightZero's `wrap_lightzero` omits FIRE-reset, so a Breakout eval episode with a non-FIRE policy never terminates and burns 108,000 steps of 50-simulation MCTS (~2 hours) per occurrence
**Date**: 2026-09-20
**File**: `/workspace/LightZero/zoo/atari/envs/atari_wrappers.py` (vendored; patch tracked at `patches/lightzero_fireset_breakout_eval_hang.patch`), `atari_qwen/scripts/run_lightzero_breakout_100k.py`
**Context**: standing up a real MCTS-based EfficientZero baseline (vendored opendilab/LightZero) to compare against our own PPO+GTrXL+EZ2-aux architecture on Atari-100k Breakout. The run was far slower than expected and my ETA estimates kept moving (2-3 days -> 21h -> 14h -> 23h), which was itself the signal that I was measuring the wrong thing.

**Three separate errors, found in order:**

| # | Error | Symptom | Reality |
|---|---|---|---|
| 1 | Launched with LightZero's shipped `collector_env_num=8` without sizing it to the box | 39 cores, only ~11 in use | Violated CLAUDE.md's "maximize hardware utilization" rule. But raising it to 24 made throughput *worse*, which disproved my own diagnosis |
| 2 | Set `reanalyze_ratio=1.0` (LightZero ships `0.`) on an unverified recollection of the paper, and wrote a confident config comment asserting their default "is tuned for the 500k-step regime" | 3.6s per training iteration | Every batch re-ran fresh 50-sim MCTS over all 256 sampled trajectories. Reverting to the shipped default gave a measured **3.2x** iteration speedup (not the "20-70x" I initially speculated -- that figure compared against a theoretical ideal, not a measurement) |
| 3 | **The real dominant cost**: `wrap_lightzero` never applies `FireResetWrapper` | One eval episode ran 12:21->14:19 (~2 hours) while the other two eval envs in the same cycle finished in seconds | Root cause below |

**Root cause (error 3)**: `wrap_lightzero` imports `FireResetWrapper` but never calls it, unlike `wrap_deepmind` and `wrap_deepmind_mr` in the *same file*, which both apply it immediately after `EpisodicLifeWrapper`. At eval time `episode_life=False`, so on Breakout: policy never selects FIRE -> ball never launches -> no life is ever lost -> episode runs to the full `TimeLimit` with a 50-simulation MCTS on every step. Compounding it, LightZero's `eval_max_episode_steps=1.08e5` is **agent** steps, which at frameskip 4 is 432,000 frames -- 4x the standard Atari 108,000-frame (27,000-step) evaluation cap.

**Fix**: (a) apply `FireResetWrapper` in `wrap_lightzero`, mirroring `wrap_deepmind`'s ordering and its `'FIRE' in get_action_meanings()` guard exactly; (b) set `eval_max_episode_steps=int(2.7e4)` in our config, which is *more* protocol-compliant than the default, not less.
**Verification** (isolated smoke test, worst case = NOOP-only policy, the exact condition that hung): `lives_start=5 -> lives_now=4 after 24 steps`. Pre-patch the same policy would run 108,000 steps. Confirmed in the live run immediately after relaunch: eval episodes now finish in seconds with sane lengths (247 steps) and non-zero rewards (3.0).

**Measurement lesson, and the reason this took three attempts**: I was reading `avg_envstep_per_sec` (~26/s) as the throughput number. That counter only covers the collect phase, which is ~3% of wall clock -- the true end-to-end rate was 0.79 steps/sec, a 33x discrepancy. Because I was watching a metric that excluded the actual bottleneck, I first blamed CPU parallelism (wrong -- CPU was 68% idle), then GPU contention (partly real: freeing one CARLA job measurably moved 3.5 -> 5.1 steps/sec, a 1.45x gain, so my "MCTS is latency-bound so more GPU won't help" hypothesis was also wrong). Only building a full timestamped step-rate curve from the log exposed the 7,197-second gap with 268 steps that was the actual story. **Build the rate curve before theorizing about the bottleneck.**

**Thesis-relevant finding (not a bug)**: even fully fixed, EfficientZero is ~25x more wall-clock-expensive per env step than our reactive PPO policy (which covered the same 100k steps in ~20 minutes), because it runs 50 sequential tree simulations per action. That compute-vs-sample-efficiency tradeoff is the honest framing for comparing the two approaches -- they do not cost the same, and presenting scores side by side without it would be misleading.
**Next**: Atari-100k requires multiple seeds (5 standard, 3 minimum); a single-seed number is not a valid benchmark result. Once the CARLA runs free the GPU, run seeds 1 and 2 concurrently rather than trying to make one run faster.
